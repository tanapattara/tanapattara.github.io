# Rendering, Cache และ Revalidation

Next.js สามารถสร้างบางส่วนล่วงหน้าเพื่อความเร็ว และสร้างบางส่วนตอนมี request เพื่อข้อมูลที่สด การออกแบบที่ดีจึงไม่ได้เลือกเพียง SSR หรือ SSG ทั้งเว็บไซต์ แต่เลือกตามความต้องการของแต่ละข้อมูลและ component

## แบบจำลองพื้นฐาน

| รูปแบบ | สร้างเมื่อใด | ตัวอย่าง |
| --- | --- | --- |
| Prerender | ตอน Build หรือก่อนผู้ใช้ร้องขอ | หน้า About, บทความที่ไม่เปลี่ยนบ่อย |
| Dynamic Rendering | ตอน request | ตะกร้าของผู้ใช้, Dashboard ส่วนตัว |
| Streaming | ส่ง Layout/ส่วนที่พร้อมก่อน | Dashboard ที่มีหลาย query |
| Client Rendering | หลัง JavaScript ทำงานใน Browser | autocomplete, interactive chart |

Server Component ไม่ได้หมายความว่าเป็น Dynamic เสมอ และ Client Component ไม่ได้หมายความว่าไม่มี HTML จาก Server การเลือก rendering กับการเลือก component boundary เป็นคนละเรื่อง

## ข้อมูลที่ต้องสดตาม Request

API ที่เปลี่ยนบ่อยสามารถระบุไม่ให้ Browser/HTTP cache เก็บผล

```tsx
async function getStock(bookId: string) {
  const response = await fetch(`https://api.example.com/stock/${bookId}`, {
    cache: 'no-store',
  })

  if (!response.ok) throw new Error('โหลดสต็อกไม่สำเร็จ')
  return response.json() as Promise<{ remaining: number }>
}
```

การอ่าน `cookies()` หรือ `headers()` เป็นข้อมูลตาม request และต้อง `await` ใน Next.js รุ่นปัจจุบัน

```tsx
import { cookies } from 'next/headers'

export default async function CartPage() {
  const cookieStore = await cookies()
  const cartId = cookieStore.get('cart-id')?.value

  return <p>Cart: {cartId ?? 'ยังไม่มีตะกร้า'}</p>
}
```

## Cache Components ใน Next.js 16

เปิดความสามารถใน `next.config.ts`

```tsx
import type { NextConfig } from 'next'

const nextConfig: NextConfig = {
  cacheComponents: true,
}

export default nextConfig
```

กำหนด function ที่ cache ได้ด้วย `'use cache'`

```tsx
// lib/categories.ts
import { cacheLife, cacheTag } from 'next/cache'

export async function getCategories() {
  'use cache'
  cacheLife('hours')
  cacheTag('categories')

  const response = await fetch('https://api.example.com/categories')
  if (!response.ok) throw new Error('โหลดหมวดหมู่ไม่สำเร็จ')
  return response.json()
}
```

- `cacheLife` กำหนดอายุของข้อมูล
- `cacheTag` ตั้งชื่อกลุ่ม cache เพื่อ invalidate เฉพาะข้อมูลที่เกี่ยวข้อง
- อย่า cache ข้อมูลเฉพาะผู้ใช้โดยไม่รวม identity ใน key เพราะอาจทำให้ข้อมูลรั่วข้ามผู้ใช้

## Revalidation หลัง Mutation

ใช้ `revalidatePath` เมื่อต้องการให้ route อ่านข้อมูลใหม่

```tsx
'use server'

import { revalidatePath } from 'next/cache'

export async function updateBook(formData: FormData) {
  await requireAdmin()
  await saveBook(formData)
  revalidatePath('/books')
}
```

ถ้าข้อมูลเดียวกันปรากฏหลายหน้า ให้ตั้ง cache tag และ invalidate ด้วย API ที่เหมาะกับรูปแบบ cache ของโปรเจกต์ แทนการระบุ path ทีละหน้า

## Loading และ Partial Prerendering

เมื่อเปิด Cache Components ให้ครอบส่วนที่ใช้ข้อมูล runtime ด้วย `Suspense` เพื่อให้ส่วน static แสดงก่อน

```tsx
import { Suspense } from 'react'

export default function BookPage() {
  return (
    <main>
      <h1>ร้านหนังสือ</h1>
      <CategoryMenu />
      <Suspense fallback={<p>กำลังตรวจสอบสต็อก...</p>}>
        <LiveStock />
      </Suspense>
    </main>
  )
}
```

`CategoryMenu` อาจ cache ได้หลายชั่วโมง แต่ `LiveStock` อ่านข้อมูลตาม request ทั้งสองส่วนจึงมีนโยบายต่างกันในหน้าเดียว

## Static Export

Static Export สร้าง HTML ตอน Build และไม่มี Server สำหรับ ISR หรือ on-demand revalidation หลัง deploy ข้อมูลที่เปลี่ยนต้องใช้วิธีใดวิธีหนึ่ง:

1. Build และ deploy เว็บไซต์ใหม่
2. ให้ Client เรียก API ภายนอก
3. เปลี่ยน hosting เป็น Node.js/Vercel ที่รองรับ Server runtime

## แบบฝึกหัด

จำแนกข้อมูลร้านหนังสือต่อไปนี้ว่า cache ได้นานเพียงใด: รายชื่อหมวดหมู่, ราคาปัจจุบัน, สต็อก, ประวัติคำสั่งซื้อ และชื่อผู้ใช้ จากนั้นสร้างหน้าเดียวที่มีทั้งข้อมูล cache และข้อมูล runtime พร้อม Suspense fallback
