# สัปดาห์ 14: Build, Release และ Presentation

สัปดาห์สุดท้ายเปลี่ยน Campus Events Mobile จากโปรเจกต์ที่รันในเครื่องให้เป็น release candidate ที่ทำซ้ำได้ มี configuration, version, assets, environment และหลักฐานการทดสอบครบ

## ผลลัพธ์การเรียนรู้

- ตั้งค่า app identity, icon, splash, scheme และ permissions
- แยก Development, Preview และ Production profiles
- จัดการ environment variables โดยไม่ฝัง secret ใน client
- สร้าง Android/iOS build ด้วย EAS
- อธิบายขอบเขตและความเสี่ยงของ EAS Update
- นำเสนอผลิตภัณฑ์พร้อมหลักฐานคุณภาพและ known issues

## Configuration ที่ต้อง freeze

| รายการ | ตัวอย่าง |
| --- | --- |
| App name | Campus Events |
| Android package | `th.ac.example.campusevents` |
| iOS bundle ID | `th.ac.example.campusevents` |
| Scheme | `campusevents` |
| Version | `1.0.0` |
| Build number/versionCode | เพิ่มทุกครั้งที่ส่ง store build |

ตรวจ icon, adaptive icon, splash, permission descriptions และ deep link scheme บนเครื่องจริง

## EAS profiles

```json
{
  "build": {
    "development": {
      "developmentClient": true,
      "distribution": "internal",
      "channel": "development"
    },
    "preview": {
      "distribution": "internal",
      "channel": "preview"
    },
    "production": {
      "autoIncrement": true,
      "channel": "production"
    }
  }
}
```

| Profile | ใช้เมื่อ | ผู้ใช้หลัก |
| --- | --- | --- |
| Development | พัฒนา/debug native modules | นักพัฒนา |
| Preview | UAT/ตรวจงานก่อน release | ทีม ผู้สอน ผู้ทดสอบ |
| Production | ส่ง store หรือ release จริง | ผู้ใช้ปลายทาง |

ก่อนสร้าง Preview/Production Build ให้ติดตั้งและตั้งค่า EAS Update เพื่อให้ binary มี update URL, project ID และ runtime policy ที่ถูกต้อง:

```bash
npx expo install expo-updates
npx eas-cli@latest update:configure
```

คำสั่ง `update:configure` จะเพิ่มค่าจริงของโปรเจกต์ใน app config ตัวอย่างโครงสร้างผลลัพธ์ที่เป็น JSON ถูกต้อง:

```json
{
  "expo": {
    "name": "Campus Events",
    "slug": "campus-events",
    "version": "1.0.0",
    "runtimeVersion": {
      "policy": "appVersion"
    },
    "updates": {
      "url": "https://u.expo.dev/PROJECT_ID"
    },
    "extra": {
      "eas": {
        "projectId": "PROJECT_ID"
      }
    }
  }
}
```

อย่าพิมพ์ `PROJECT_ID` ตามตัวอย่าง ให้ใช้ค่าที่ EAS สร้างให้และ commit เฉพาะ configuration ที่ไม่ใช่ secret

## Build commands

ไม่จำเป็นต้องติดตั้ง EAS CLI แบบ global

```bash
npx eas-cli@latest login
npx eas-cli@latest build:configure
npx eas-cli@latest build --platform android --profile preview
npx eas-cli@latest build --platform android --profile production
```

iOS production build ต้องมี Apple Developer account และ signing ที่เหมาะสม หากรายวิชาเน้น Android ให้ส่ง iOS configuration/release plan แทน artifact ตามทรัพยากรที่มี

## Environment และ Secrets

- ค่า `EXPO_PUBLIC_*` จะอ่านได้จาก client bundle จึงไม่ใช่ secret
- แยก API URL ของ preview/production
- เก็บ server secret ที่ backend หรือ secret manager
- ตรวจว่า log, source map, test account และ debug menu ไม่เปิดเผยข้อมูลเกินจำเป็น

## EAS Update

EAS Update ส่ง JavaScript/assets ที่เข้ากันกับ native runtime เดิมได้ เหมาะกับ bug fix ในส่วน JS แต่ไม่แทน store build เมื่อเปลี่ยน native dependency, permission, app identity หรือ native configuration

### Branch, Channel และ Runtime Version

- **Branch** เก็บลำดับของ update groups เช่น branch สำหรับ preview หรือ production
- **Channel** ถูกฝังใน native build และชี้ไป branch ที่ build นั้นควรรับ update
- **Runtime version** ป้องกันไม่ให้ build ดาวน์โหลด update ที่ต้องใช้ native code คนละชุด

`eas.json` ด้านบนผูก Preview Build กับ channel `preview` และ Production Build กับ channel `production` หลังตั้งค่าและสร้าง build แล้วจึงเผยแพร่ update:

```bash
npx eas-cli@latest update --channel preview --message "แก้ empty state"
```

| การเปลี่ยนแปลง | EAS Update ได้ | ต้องสร้าง Native Build ใหม่ |
| --- | :---: | :---: |
| ข้อความ, TypeScript logic, style, bundled image | ✓ | |
| เพิ่ม/อัปเดต native module | | ✓ |
| เปลี่ยน permission หรือ config plugin | | ✓ |
| เปลี่ยน app icon, package/bundle ID หรือ signing | | ✓ |

ก่อนส่ง production ให้เผยแพร่ที่ preview channel และทดสอบกับ build ที่ใช้ runtime เดียวกัน หาก update มีปัญหา ให้หยุด rollout และ republish update group ที่ทราบว่าเสถียรจาก EAS dashboard พร้อมบันทึกเหตุการณ์และ regression test

<Callout type="warning">
  `eas update:configure` และการสร้าง build ที่มี `expo-updates` ต้องเกิดก่อนการสาธิต OTA ตรวจ runtime compatibility, rollback plan และนโยบายของแพลตฟอร์มเสมอ
</Callout>

## Release checklist

- [ ] Typecheck, lint, tests และ Expo Doctor ผ่าน
- [ ] Clean install และ migration จากรุ่นก่อนทำงาน
- [ ] Login, Offline, Permission denied, Notification และ Deep link ผ่าน smoke test
- [ ] Preview และ Production ใช้ environment ที่ถูกต้อง
- [ ] Version/build number และ release notes ถูกต้อง
- [ ] ไม่มี secret, debug endpoint หรือ test data หลุดไปใน build
- [ ] Privacy/permission descriptions ตรงกับพฤติกรรมจริง
- [ ] README ระบุ setup, architecture, environments, tests และ known issues

## Definition of Done

- [ ] Clean install เปิดและทำ flow หลักได้

- [ ] OTA demo ไม่เปลี่ยน native compatibility
